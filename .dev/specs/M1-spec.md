# M1 Spec — Full round loop

## Goal

Restated exit criterion (roadmap M1): **strangers can complete a full round start→finish and someone wins.** Measurable success when an automated headless simulation with 4–6 Colyseus clients proves the entire loop without browsers — lobby gather → secret roles → timed shift with prep/unprep/fake-prep and elevator teleports → buzzer or attrition win → results with winner banner + traitor reveal — and a small manual two-browser check on the local or deployed build confirms a human can play that same loop to a win.

## Scope

**In (M1 adds on top of M0 walking skeleton):**
- All 3 floors × 7–8 rooms (~24 rooms total) with grand lobby; hall layout locked; floor membership server-authoritative, floor changes only via elevator (roadmap M1 bullet 1; FR-3).
- Elevators as **teleport buttons first** — no car animation in M1 — deterministic cycle: call button → car arrives in **3 s** → ride takes **2 s**, **capacity 2 per car**, two shafts at opposite ends of each floor, queues handled server-side (FR-5; PRD §7 `ELEVATOR_ARRIVE_MS=3000`, `ELEVATOR_RIDE_MS=2000`, `ELEVATOR_CAPACITY=2`).
- Role assignment: **1 secret saboteur**, rest staff, assigned at lobby gather-up spawn on round start; lobby size gating **≥4 players** to start (FR-2; roadmap bullet 3).
- Prep action: hold **inside room**, **5 s** channel, **clean→prepped** (FR-7; `PREP_TIME_MS=5000`).
- Unprep action: **saboteur only**, **3 s** channel, **prepped→trashed**, **re-trash allowed** (trashed→trashed with another 3 s) (FR-8; `UNPREP_TIME_MS=3000`).
- Fake prep available to saboteur with **identical visuals/duration** to real prep but no state change (FR-9).
- Win checks: **≥80% coverage at 5:00 buzzer** (`SHIFT_LENGTH_S=300`, `COVERAGE_TARGET=0.8`) **and staff down to 1 attrition** immediate saboteur win (PRD §6.6; roadmap bullet 7).
- Results screen v1: **winner banner (staff|saboteur) + traitor reveal** (sessionId + display name) and nothing else (FR-21).
- Server authority preserved: all rule-bearing state stays server-side; positions remain client-reported presence with max-speed + teleport sanity clamp; no physics (techstack §1, §6).
- Tuning constants remain single-sourced in `@grandhotel/shared` (techstack §5).

**Out (explicit non-goals, deferred):**
- Evidence layer (M2): door status cards permanent on prep (FR-11), trash freshness two tiers fresh ≤75 s → settled + sprite swap (FR-12, `FRESHNESS_WINDOW_MS`), coverage % meter always-visible HUD (FR-14), public elevator position panels both shafts readable (FR-6), rustle audio ~3 tiles (FR-13), and the M2 ruling that voluntary walk-out mid-unprep cancels cleanly is already covered by M1 channel-cancel semantics but the M2 audio/panels/cards are out.
- Justice + recap (M3): walk-in instant fire (FR-15), accusation hold-E within ~2 tiles same floor with confirm menu (FR-17), grace-period rule accusing before first unprep fires accuser (FR-18), wrong/correct accusation firing (FR-18/FR-19), spectator cam full-building overview (FR-20), event-log recap timeline (FR-22).
- Telemetry & KPIs: JSONL per-round log (FR-23) and post-round KPI script (FR-24) — built incrementally M1–M3 per roadmap, **not required to gate M1**.
- PRD §4 Non-Goals still out: art/audio polish, integrated/spatial voice, text chat, matchmaking/accounts/progression/monetization, mobile/touch, multiple maps, extra roles/utility tools.
- Reconnection/session-resume UX beyond bare Colyseus token (deferred).

## Requirements

- **R-1:** The building is server-authoritative with a grand lobby plus 3 guest floors × 7–8 rooms each, totaling 22–24 rooms, with a fixed hallway layout; the server owns each room's bounds, its state (`clean|prepped|trashed`), and each player's floor membership, and floor changes occur only via elevator events. (source: FR-3, roadmap M1 bullet 1, PRD §7 rooms ~24)
- **R-2:** Horizontal movement on any floor remains strictly left/right along the hallway strip, pass-through bodies with no collision, Phaser Arcade Physics stays disabled, position clamped to per-floor hallway bounds, and vertical position never changes except by elevator teleport. (source: FR-4, techstack §6, roadmap M1)
- **R-3:** Two elevator shafts at opposite ends of each floor operate as deterministic teleports: call → car arrives in exactly `ELEVATOR_ARRIVE_MS = 3000` ms → ride takes `ELEVATOR_RIDE_MS = 2000` ms to a chosen destination floor; each car capacity is `ELEVATOR_CAPACITY = 2` with server-side seat reservation and queuing; no car animation is required in M1. (source: FR-5, PRD §7 elevator rows, roadmap bullet 2)
- **R-4:** The host can start the round only when ≥4 players are present; a start attempt with <4 is rejected server-side with an error observable by the requester and the phase stays `waiting`; on successful start all players spawn at the lobby gather-up position. (source: FR-2, PRD §7 players 4–6, roadmap)
- **R-5:** On transition `waiting → playing` the server assigns exactly one secret saboteur uniformly at random among present players (rest staff), delivers each role only to its owner via a private message/state field, never exposes any player's role in broadcast state, and reveals the saboteur identity only inside the final `results` payload. (source: FR-2, roadmap bullet 3)
- **R-6:** Any player who is **inside** a room whose state is `clean` may start a prep channel that completes after exactly `PREP_TIME_MS = 5000` ms of continuous hold, transitioning that room `clean→prepped` server-side; leaving the room, changing floor, or releasing early cancels with no state change. (source: FR-7, PRD §7 prep 5s, roadmap)
- **R-7:** Only the saboteur who is inside a room whose state is `prepped` (or already `trashed` for re-trash) may start an unprep channel that completes after exactly `UNPREP_TIME_MS = 3000` ms to transition `prepped→trashed` (or `trashed→trashed` for re-trash, unlimited); a staff unprep attempt is rejected server-side; early exit cancels with no state change. (source: FR-8, PRD §7 unprep 3s, roadmap)
- **R-8:** The saboteur may start a fake-prep channel of exactly `PREP_TIME_MS = 5000` ms in any room state; it produces client visuals indistinguishable from real prep and leaves the room state unchanged on completion. (source: FR-9, roadmap bullet fake prep identical visuals)
- **R-9:** Any active channel (prep / unprep / fake-prep) is exclusive per player and any voluntary walk-out, floor change, or explicit cancel cleanly aborts it with the room unchanged, no trace, and no firing. (source: FR-7/FR-8/FR-9, techstack §1 authority)
- **R-10:** Room state (`clean|prepped|trashed`) and channel progress are readable only while the observing player is **inside** that room; clients outside the room (including hallway on same floor) receive no interior state, and doors auto-open on entry to reveal it. (source: FR-10 scoped to M1 states)
- **R-11:** The shift timer runs `SHIFT_LENGTH_S = 300` s server-side from `playing` entry; at 0 (buzzer) the server computes `coverage = preppedCount / totalRooms` and declares **staff win if coverage ≥ `COVERAGE_TARGET = 0.8`, otherwise saboteur win**; timer and coverage are server-authoritative. (source: PRD §6.6, roadmap bullet win checks, PRD §7 shift 5:00 + 80%)
- **R-12:** If the number of non-disconnected staff (and in M3, non-fired) drops to 1, the server immediately ends the round with a **saboteur attrition win**, regardless of timer; in M1 the trigger is reachable via disconnect/leave down to 1 and is wired so future firing will reuse the same check. (source: PRD §6.6, roadmap bullet attrition loss, PRD §7 attrition)
- **R-13:** On any terminal win condition the server transitions to `results` and broadcasts a v1 results payload containing **winner (`staff` or `saboteur`) and traitor reveal (`saboteurSessionId` + display name matching the earlier assignment)**; no M3 recap timeline is required in M1. (source: FR-21, roadmap bullet results v1)
- **R-14:** All rule-bearing state (roles, room states, channels and their timers, elevator queues and positions, shift timer, coverage, winner) lives server-side in Colyseus Schema and is never decided by the client; avatar positions remain the documented techstack §1 exception — client-reported presence, sanity-clamped (`SERVER_MAX_SPEED_PX_S × dt` and floor changes only via elevator events) — and failure to meet a clamp never corrupts rule state. (source: techstack §1 + §6, PRD §7)
- **R-15:** Every M1 tuning value used (players, shift, prep/unprep, coverage, elevator arrive/ride/cap) is imported from `@grandhotel/shared` constants and no literal `6`, `300`, `5000`, `3000`, `0.8`, `2000`, `2` appears in server or client source as a tuning value outside the shared package. (source: techstack §5, PRD §7 single source of truth)

## Verification Criteria

- **V-1 (covers R-1):** Automated: `pnpm --filter @grandhotel/server test -- -t "building topology"` and `pnpm --filter @grandhotel/shared test -- -t "topology"` together assert (a) the server constructs a building with 1 lobby + 3 floors, each floor 7–8 rooms, total `ROOM_COUNT` 22–24 exported from `@grandhotel/shared`, and (b) a headless `HotelRoom` join + floor-membership query shows a player on floor 0 is not reported inside any floor-1 room; hallway bounds exist per floor via shared constants. Fails if room count is outside 22–24 or any room lacks a floor assignment.
- **V-2 (covers R-2):** Automated: `pnpm --filter @grandhotel/client test -- -t "horizontal clamp"` reuses the M0 movement unit but extended to all floors — asserts held-right converges to that floor's `HALLWAY_MAX_X`, held-left to `HALLWAY_MIN_X`, y is invariant (no y param), and two co-located avatars on the same floor move independently with pass-through; plus `pnpm --filter @grandhotel/server test -- -t "position clamp"` asserts `computeClampedX` still clamps any floor's movement by `SERVER_MAX_SPEED_PX_S × dt`. Both suites must exit 0.
- **V-3 (covers R-3):** Automated headless: `pnpm --filter @grandhotel/server test -- -t "elevator deterministic"` uses Vitest fake timers (`vi.useFakeTimers()`) — a client calls elevator on floor 0, asserts the car is not yet available at t+2999 ms, is available at t+3000 ms ±50 ms, a subsequent `ride` of 2000 ms places the rider(s) on the requested destination floor, and a third concurrent rider when capacity 2 is already seated is queued/rejected. Also asserts `ELEVATOR_ARRIVE_MS`, `ELEVATOR_RIDE_MS`, `ELEVATOR_CAPACITY` equal the shared constants. Suite must be green.
- **V-4 (covers R-4):** Automated: `pnpm --filter @grandhotel/server test -- -t "start gating"` — with 3 joined clients a `startRound` message from host is rejected (error surfaced, phase stays `waiting`); with 4 joined it succeeds (`waiting→playing`), and all 4 clients' projected state shows positions inside lobby gather-up bounds. Integration complement: `pnpm --filter @grandhotel/tooling test:integration -- -t "m1 start gating"` does the same over real `colyseus.js` clients on an ephemeral server.
- **V-5 (covers R-5):** Automated: `pnpm --filter @grandhotel/server test -- -t "role assignment"` runs 200 randomized assignments (seeded) and asserts each round has exactly one `saboteurSessionId`; a two-client integration `pnpm --filter @grandhotel/tooling test:integration -- -t "m1 roles secret"` creates a 4-player room, starts, then collects each client's `RoomStateView` — asserts the saboteur's client sees `myRole === 'saboteur'` while every non-saboteur client sees `myRole === 'staff'` and never receives another player's role field (`otherRole` is undefined/null in their projection).
- **V-6 (covers R-6):** Automated: `pnpm --filter @grandhotel/server test -- -t "prep channel"` with fake timers — a player inside a `clean` room starts prep, asserts room still `clean` at t+4999 ms, `prepped` at t+5000 ms, and that moving out at t+2500 ms leaves it `clean`; a second client outside that room never observes the interior state. Uses `PREP_TIME_MS` from shared.
- **V-7 (covers R-7):** Automated: `pnpm --filter @grandhotel/server test -- -t "unprep and re-trash"` — saboteur inside `prepped` room completes 3000 ms → `trashed`; staff attempt on same room rejected with observable error and room stays `prepped`; saboteur re-trashes `trashed→trashed` after another 3000 ms succeeds; early walk-out at 1500 ms leaves room `prepped`. Asserts timings equal `UNPREP_TIME_MS`.
- **V-8 (covers R-8):** Automated: `pnpm --filter @grandhotel/server test -- -t "fake prep identical"` — saboteur starts fake-prep in a `clean` room, asserts room is `clean` at t+4999 ms and still `clean` at t+5000 ms (no state change), and asserts `fakePrepDuration === PREP_TIME_MS` and its completion timestamp equals a real prep's duration within 1 ms. Manual supplement (30 s glance) that the client plays the same animation for both — justified as visual identity is perceptual, while timing indistinguishability is already automated here.
- **V-9 (covers R-9):** Automated: `pnpm --filter @grandhotel/server test -- -t "channel cancel cleanly"` — starts each channel type (prep / unprep / fake-prep), then triggers walk-out, elevator ride, and explicit cancel; asserts in every case the room state is unchanged, no residual channel remains (`activeChannel === null`), and no win or firing side-effect occurred. Suite green is required.
- **V-10 (covers R-10):** Automated integration: `pnpm --filter @grandhotel/tooling test:integration -- -t "m1 room observability"` — client A inside room R while client B stays in same-floor hallway; spy on each client's `RoomStateView` room-projection (or onState delta). Asserts A sees `rooms[R].state ∈ {clean,prepped,trashed}` while B sees `rooms[R].state === undefined/null` or is omitted. Moving B into R then shows B now sees it. Server unit `pnpm --filter @grandhotel/server test -- -t "room visibility"` mirrors the same with direct `RoomState` inspection.
- **V-11 (covers R-11):** Automated with accelerated clock (fake timers or injected shorter `SHIFT_LENGTH_S` for tests only, documented in test): `pnpm --filter @grandhotel/server test -- -t "buzzer coverage win"` has two subcases — (a) pre-prepare ≥80% of rooms (e.g. 20/24) then advance mock time to `SHIFT_LENGTH_S` → asserts `phase === 'results'` and `winner === 'staff'`; (b) prepare <80% (e.g. 12/24) → `winner === 'saboteur'`. Also asserts mid-shift `winner` is still `null`. Integration `pnpm --filter @grandhotel/tooling test:integration -- -t "m1 buzzer"` repeats (a) over real clients with a shortened shift configured for the test server.
- **V-12 (covers R-12):** Automated: `pnpm --filter @grandhotel/server test -- -t "attrition win"` — start a 4-player round, disconnect two clients so only 1 staff-connected player remains (or leave via `onLeave`), asserts the room immediately transitions to `results` with `winner === 'saboteur'` before the timer expires. Integration `pnpm --filter @grandhotel/tooling test:integration -- -t "m1 attrition"` does the same with real `client.disconnect()` calls.
- **V-13 (covers R-13):** Automated: `pnpm --filter @grandhotel/server test -- -t "results v1 reveal"` — after either V-11 or V-12 win, asserts every connected client's `RoomStateView` (or schema) shows `phase === 'results'`, `winner ∈ {staff,saboteur}`, and `traitorReveal.sessionId` equals the saboteur assigned in V-5 with matching display name. Also asserts `FR-22` recap fields are absent. Integration `pnpm --filter @grandhotel/tooling test:integration -- -t "m1 full round loop"` as the exit-criterion micro-round: 4 clients, start, saboteur unpreps one prepped room, wait for buzzer (accelerated), assert both V-11 and V-13 payloads together.
- **V-14 (covers R-14):** Automated: `pnpm -r typecheck && pnpm -r build` exit 0; `pnpm --filter @grandhotel/server test -- -t "authority"` asserts that spoofed client messages cannot set roles, room states, timers, elevator positions, coverage, or winner — the handler rejects them and server state is unchanged; the position-clamp sub-assertion reuses V-2's `SERVER_MAX_SPEED_PX_S × dt` rejection. `onState` projection check confirms `GameClient` consumers never import `colyseus.js` types directly (grep `from "colyseus"` in `apps/client/src/game` and `apps/client/src/ui` returns empty).
- **V-15 (covers R-15):** Automated: `pnpm --filter @grandhotel/shared test -- -t "tuning constants"` asserts each exported constant equals the PRD §7 table value (`MAX_PLAYERS=6`, `SHIFT_LENGTH_S=300`, `PREP_TIME_MS=5000`, `UNPREP_TIME_MS=3000`, `COVERAGE_TARGET=0.8`, `ELEVATOR_ARRIVE_MS=3000`, `ELEVATOR_RIDE_MS=2000`, `ELEVATOR_CAPACITY=2`). Then `grep -R --include="*.ts" -E '\b(MAX_PLAYERS|SHIFT_LENGTH_S|PREP_TIME_MS|UNPREP_TIME_MS|COVERAGE_TARGET|ELEVATOR_ARRIVE_MS|ELEVATOR_RIDE_MS|ELEVATOR_CAPACITY)\b' apps/client/src apps/server/src | grep -v "import" | grep -v "from.*shared" | wc -l` must be 0, and a literal sweep `grep -Rn " 6\b.*cap\|5000\|3000.*unprep\|0\.8\|300.*shift" apps/server/src apps/client/src` returns only comments importing via shared when inspected. Manual audit of the grep output is allowed (~1 min) to excuse non-tuning numeric 6s that are not cap-related.

*Automated vs manual split:* V-1–V-7, V-9–V-15 are fully automated (Vitest unit + headless Colyseus integration, `pnpm -r typecheck/build/test`, `pnpm --filter @grandhotel/tooling test:integration`). V-8 is automated for timing with a 30-second justified visual glance that fake-prep looks identical. The end-to-end V-13 micro-round also supplies the roadmap's "strangers complete a full round, someone wins" without requiring real strangers — strangers are modeled by independent colyseus.js clients, which is permitted by the project's testing strategy (tooling integration tests spawn a real server on an ephemeral port).

## Assumptions & Open Questions

**Assumptions (resolved from docs, listed for audit; planner may finalize within stated tolerances):**
1. **Room count & distribution:** exactly **24 rooms, 8 per floor** satisfies "3 floors × 7–8 rooms (~24)"; a planner choosing 7 on one floor (23) or 7 on two floors (22) is still within spec tolerance 22–24, but the suite asserts the chosen total so coverage denominator is stable for V-11.
2. **Hallway geometry:** each floor's hallway shares the M0 free-variable bounds (`HALLWAY_MIN_X=96`, `HALLWAY_MAX_X=864`, `HALLWAY_Y` per floor is `HALLWAY_Y + floor*FLOOR_Y_STEP`); room x-ranges are non-overlapping intervals partitioning the hall. Planner fixes exact `FLOOR_Y_STEP` and per-room intervals.
3. **Lobby:** a single ground-floor lobby distinct from guest floors; gather-up spawn is at lobby center; clients start there on `playing` entry even if they were in hallway during `waiting`.
4. **Elevator shafts:** two shafts (A at west end, B at east end) each with one car that moves independently; calling is per-shaft, riding chooses a destination floor among {lobby,1,2,3}; in M1 the destination is any floor — no restriction that a car must already be on the caller's floor. Queue is FIFO per shaft, capacity 2 enforced per ride (two riders teleport together if they board together).
5. **Channel input:** hold is a single key (e.g. hold E) that must be held continuously; releasing, moving out of room bounds, or triggering an elevator ride cancels; network jitter is not a cancel — only server-observed leave/ride does.
6. **Timer acceleration for tests:** real `SHIFT_LENGTH_S=300` s is not waited in CI; tests may inject a shorter shift (e.g. 10 s) via constructor/config or use Vitest fake timers to fast-forward; production build still uses 300 s and V-11's production constant assertion guards against drift.
7. **Attrition reachability in M1:** without M3 firing, staff dropping to 1 can only be reached by disconnect/leave in M1; the win check is still required and is proven via those leaves so that when M3 adds firing it reuses the same path without spec change.
8. **Room-state vocabulary in M1:** only `clean|prepped|trashed`; M2's `fresh|settled` freshness tiers are not present, and hallway cards do not exist yet, so reading is simply the current state while inside.
9. **Role secrecy channel:** role is sent as a private `onMessage` or a per-client `PlayerState` private field, never as part of the replicated `RoomState.players` map; re-broadcast inspection in V-5 proves secrecy.

**Open questions for orchestrator (none blocking — spec is build-ready):**
- *Deploy URL for live V-13 glance:* same as M0, `PUBLIC_URL` in `STATE.md` + `deploy/README.md` is still operator-pending, but every M1 V-criterion can run locally via `tooling` ephemeral server; live two-browser check remains a manual supplement that reuses M0's `pnpm smoke:local` harness.
- *Tile size for range checks not yet needed:* `TILE_SIZE_PX`, `ACCUSATION_RANGE_TILES`, `RUSTLE_RANGE_TILES` are defined but have no M1 behavior; they are carried from shared constants for V-15 completeness.

**No BLOCKING questions.** All PRD §7 numbers needed for M1 are fixed above; any remaining free variables (exact room rectangles, lobby center) are within planner discretion and do not change the meaning of any R or V.
